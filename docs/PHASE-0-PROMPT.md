## 8. Functional requirements

1. **Env**: `src/lib/env.ts` validates everything at startup with actionable errors. `.env.example` documents every variable with placeholders only: `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET`.
2. **DB client**: server-only module using the service role key; guard against client imports (`server-only`); typed with the generated types.
3. **`GET /api/health`**: JSON `{ status, time, db: "ok" | "error", lastSync: null }`; 200 when healthy, 503 when the DB is unreachable; short timeout on the DB check; no caching; never leaks secrets or error internals.
4. **Security headers** in Next config (CSP suited to current needs, HSTS, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, frame-ancestors). Explain the CSP in an ADR.
5. **Logger**: structured JSON, request id support, email masking (unit-tested).
6. **CI** (`ci.yml`) on PR and on push to `main`: install with cache → lint → typecheck → unit → build → local Supabase start + apply all migrations from scratch → Playwright e2e (incl. axe) → secret scan (e.g., gitleaks) → `pnpm audit` (report-only for now). A red CI blocks merging.
7. **Production migrations** (`db-migrate.yml`): runs on `main`, uses GitHub Environment `production` with required manual approval, applies migrations with secrets from that environment. Document the required secrets. It stays inactive until the owner creates the production project and secrets.
8. **Vercel** documented in the README (import repo; env vars per environment; Preview → staging Supabase, Production → production Supabase). Add `vercel.json` only if truly needed.
9. **Quality gates**: strict TS, no `any`, ESLint + Prettier, Husky pre-commit with lint-staged, PR template with checklist (tests, a11y, security, docs). Use Conventional Commits by convention; do not add commit-message enforcement tooling.

## 9. Design system and first pages (what the owner will look at)

**Design direction**: modern, friendly, clean, trustworthy; calm and spacious; plain language. Must NOT look like an official government site: no flags, eagles, seals, or the typical gov blue-and-gold. Choose a distinctive but restrained palette (e.g., a confident deep teal or indigo as primary with a warm accent on a soft neutral background), define it once.

**Tokens**: color (with accessible contrast pairs), type scale (use `next/font` or a robust system stack; max 2 families), spacing, radius, shadow, container widths. Implement as CSS variables + Tailwind theme. Light mode required; dark mode optional only if contrast is verified.

**App shell**: `SiteHeader` (wordmark from `site.ts`, nav limited to pages that exist), `SiteFooter` (About, Disclaimer, the required disclaimer text from `AGENTS.md` section 9, "Data from USAJOBS" attribution), skip-to-content link, landmarks.

**Home page** (static, server-rendered): hero with the promise "Federal jobs, explained in plain English" (or a better line in the same spirit), a clear honest status ("Under construction — job listings and alerts are coming soon"), a "How it will work" section (Find → Understand → Get alerts), and a short "What you'll get" section reflecting the owner's priorities (fresh jobs and alerts, plain-English eligibility, step-by-step guides, real pay information). **No fake jobs, fake stats, stock photos, dead buttons, or non-working forms.** Visuals via CSS/inline SVG only.

**About** and **Disclaimer** pages: real, short, honest content; Disclaimer uses the exact required text; mark "draft — legal review pending" in an HTML comment, not in the UI.

**Responsive**: verified from 360px to 1440px. Generate Playwright screenshots (mobile + desktop) of home, about, disclaimer, and 404 into `docs/screenshots/` so the owner can review quickly.

## 10. Security requirements

`AGENTS.md` section 9 applies. Here specifically: no secrets in the repo, logs, or client bundle (verify by searching the build output for the service role key pattern); RLS on every table created; CI secret scan active; the health endpoint leaks nothing.

## 11. Error handling

Env errors are explicit. `/api/health` handles DB timeout/failure without throwing. `error.tsx` and `not-found.tsx` are friendly and accessible. Unhandled errors are logged with masking.

## 12. Performance

Static rendering where possible, minimal client JS, no layout shift. Lighthouse mobile on home: Performance ≥ 95, Accessibility ≥ 95, SEO ≥ 95. Report actual numbers.
